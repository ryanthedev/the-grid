# Plan: tmux Status Dashboard (cron-driven, single-instance)

**Created:** 2026-06-16
**Status:** in-progress
**Started:** 2026-06-16
**Current Phase:** 1
**Complexity:** complex

---

## Context

There is no at-a-glance view of the state of all tmux sessions/windows — especially which
Claude windows are waiting for input (the need behind the existing `notify install-hook`).
Today that information is scattered across sessions you must attach to one by one.

This builds a recurring task that launches headless Claude Code, uses the **claude-mux `tmux`
MCP** to read every session/window, AI-summarizes each window's state, and writes a JSON
status file. A new **dedicated SwiftUI dashboard** in the existing `grid-notify` app watches
that file and renders a live session→window tree — updated the same way notifications are
(file-watch → `@Published` → SwiftUI), refreshable on demand (in-view button, `thegrid tmux
refresh` CLI, BFD hotkey), with a **mutex** so only one run happens at a time. The driver's
lifecycle is tied to the dashboard window: window open ⇒ driver running; hidden ⇒ stopped.

Reuses theGrid patterns 1:1 (verified): `NotificationPanelWindow`, `AnimationConfigWatcher`
(file-watch), `NotificationPanelViewModel` (actor/async → `@Published`), `ScriptManager`
(child-process spawn/terminate), `DetailWindowController` (pop-out), and the
CLI→server-RPC→`DistributedNotification` relay used by `notify`/`terminal`
(`GridCommandRouter.swift:1032`, `MessageHandler.swift:~1966`).

## Constraints

- New dedicated SwiftUI dashboard window in `grid-notify` (session→window tree); reuse the
  patterns above rather than inventing new infrastructure.
- Status is AI-generated by headless Claude Code driven by a **skill**, using the claude-mux
  `tmux` MCP to read panes and summarize each window.
- Status delivered via a watched JSON state file at `$XDG_STATE_HOME/thegrid/tmux-status.json`
  (same live-update mechanism as notifications); written atomically (temp + rename).
- Driver lifecycle bound to the dashboard window (window open ⇒ running; hidden ⇒ stopped).
  No launchd.
- Single instance enforced by a mutex — `flock(2)` in Swift on `tmux-status.lock`
  (macOS ships no `flock(1)` binary).
- Refresh on demand via all three: in-view button, `thegrid tmux refresh`, BFD hotkey —
  routed through CLI→grid-server RPC→`DistributedNotification`.
- Off-by-default; configurable interval (default 60s) since each tick spends a Claude run.
- grid-notify is the SwiftUI/`DispatchSource` side of the repo; the "actors-only, no SwiftUI"
  rule in `docs/code-standards.md` §8 is grid-server-scoped and does not apply here.
- Conventions: `jlog`/`JSONLogger`, no inline trailing comments, `[weak self]` + `guard let
  self`, per-module `Error, LocalizedError` enums, `PascalCase.swift` per primary type.

## Chosen Approach

**A — Driver in grid-notify (Swift `Timer` + `Process` spawn).** grid-notify owns a timer that
spawns `claude` per tick, with a `flock(2)` + in-process mutex, and AppDelegate observers that
start/stop it with the dashboard window. Wins on the two differentiators — immediate refresh
(direct in-process `refreshNow()`) and clean stop-on-hide (no cost leak) — and keeps the whole
feature inside grid-notify, which already owns SwiftUI, file-watchers, and child-process
supervision. **Fallback:** if grid-notify spawning `claude` proves unworkable, fall back to a
`ScriptManager`-supervised loop script (Approach B) signalled for refresh via a touch-file.

## Rejected Approaches

- **B — Supervised loop script via ScriptManager:** refresh-on-demand is awkward (must signal a
  running loop), lifecycle control is coarse, and restart-delay semantics aren't built for a
  tick cadence. Kept as the fallback.
- **C — Driver in grid-server:** grid-server is actor/AppKit-only with no GUI window to bind
  lifecycle to; spawning Claude from the window-manager core couples two actors and violates
  its SRP. Worst boundary fit.

## Implementation Phases

### Phase 1: Skill + data contract
**Model:** sonnet
**Skills:** aposd-designing-deep-modules, code-clarity-and-docs
**Gate:** Standard

**Goal:** Define the JSON state-file contract and author the `tmux-status` skill (plus a
slash-command fallback) so headless Claude, via the claude-mux `tmux` MCP, reliably writes a
schema-valid status file reflecting real tmux state.

**Scope:**
- IN: JSON schema definition; `.claude/skills/tmux-status/SKILL.md`; `.claude/commands/tmux-status.md`
  fallback; the `claude -p` invocation recipe; naming the two `DistributedNotification`
  constants and the lockfile path (the seams P2/P4/P5/P6 consume); verify a headless run writes
  the file.
- OUT: any Swift code; the driver that calls this (P4).

**Constraints:** Write atomically (write temp, rename). Resolve `claude` to an absolute path
(it is a python wrapper — `which claude`). The skill is an AI-facing doc — comments-first,
precise `statusKind` vocabulary.
**Edge cases:** tmux not running → write `{ "generatedAt": <ts>, "sessions": [] }`, never crash;
a pane that can't be captured → that window gets `statusKind:"error"` + the error as `summary`;
the file must never be left half-written (atomic rename).

**Approach notes:** AI summary is the deliverable (user chose this over raw dumps); keep the
contract a deep, minimal seam — callers read sessions→windows without knowing how tmux was read.
**File hints:** `.claude/skills/`, `.claude/commands/` — skill + fallback; `~/.local/state/thegrid/` — output path.
**Depends on:** nothing — entry phase | **Unlocks:** Phase 2, Phase 4
**Produces:** the JSON contract (canonical), written to `$XDG_STATE_HOME/thegrid/tmux-status.json`:
```json
{ "generatedAt": 1718500000,
  "sessions": [ { "name": "work", "attached": true,
    "windows": [ { "index": 0, "name": "nvim", "command": "nvim", "active": true,
      "statusKind": "active", "summary": "editing api.go", "target": "work:0" } ] } ] }
```
`statusKind` ∈ `active|running|waiting|idle|error`. Plus constants:
`com.thegrid.tmux.toggle`, `com.thegrid.tmux.refresh`, lockfile `$XDG_STATE_HOME/thegrid/tmux-status.lock`,
and the documented `claude -p "/tmux-status" --mcp-config … --allowedTools "mcp__claude-mux__tmux Write"
--permission-mode bypassPermissions` recipe.

**Done when:**
- [ ] DW-1.1: The JSON schema (fields, types, `statusKind` enum) is documented in the skill file.
- [ ] DW-1.2: A headless `claude` run writes a schema-valid file whose sessions/windows match
      `tmux ls` / `tmux list-windows` at that moment.
- [ ] DW-1.3: With tmux not running, the run writes `{generatedAt, sessions:[]}` (no crash, valid JSON).
- [ ] DW-1.4: The notification-name constants, lockfile path, and invocation recipe are recorded
      in the skill file for downstream phases.

**Difficulty:** MEDIUM
**Uncertainty:** Headless skill-vs-command trigger reliability — resolved here via the fallback and DW-1.2.

**Skills:** aposd-designing-deep-modules, cc-defensive-programming

**File hints:** `grid-notify/Sources/GridNotify/AnimationConfig.swift` (watcher pattern to mirror),

**Depends on:** Phase 1 | **Unlocks:** Phase 3, Phase 5

- [ ] DW-2.4: `notify.yaml` with a `tmux:` block parses into `NotifyConfig.tmux`; absent block → defaults.

### Phase 4: Driver + flock mutex
**Model:** sonnet
**Skills:** aposd-designing-deep-modules, cc-defensive-programming
**Gate:** Full
**Security-sensitive:** yes — spawns an external process with `--permission-mode bypassPermissions`; must resolve `claude` to an absolute path (mirror `resolveThegridBin`) and build arguments from hardcoded constants only, never interpolating config strings.

**Goal:** Implement `TmuxStatusDriver` — a timer that spawns the P1 `claude` run on an interval
and on demand, guaranteeing a single in-flight run via a `flock(2)` mutex.

**Scope:**
- IN: `TmuxStatusDriver.swift` (mirror `ScriptManager` spawn/terminate); `Timer` on the config
  interval; `flock(2)` (`LOCK_EX|LOCK_NB`) on the lockfile + in-process `isRunning` guard;
  `start()`, `stop()`, `refreshNow()`.
- OUT: who calls `start/stop/refreshNow` (P5); the JSON-producing skill (P1).

**Constraints:** Mutex is the defensive core — robustness strategy: on lock contention, log
`tmux.driver.skip` and return (skip the tick), never block the timer or crash. No empty catch;
surface spawn failures via `jlog`. Resolve `claude` to an absolute path. Hold the flock for the
spawned process's lifetime; release on exit. `[weak self]` in the termination handler.
**Edge cases:** lock already held (skip + log); `claude` binary missing (log `err.tmux.driver.spawn`,
do not restart-storm); `stop()` while a run is in flight (terminate process, release lock);
rapid `refreshNow()` while running (in-process guard makes it a no-op); a hung run (kill after a
timeout).

**Approach notes:** flock in Swift (`flock(fd, LOCK_EX | LOCK_NB)`), not `flock(1)` — macOS lacks
the binary. Driver is a deep module: timer + process + lock all hidden behind 3 methods.
**File hints:** `ScriptManager.swift` (spawn/terminate/restart pattern), `NotifyConfig.swift`
(config), `NotifyCommand.swift:resolveThegridBin` (absolute-path resolution pattern).
**Depends on:** Phase 1 | **Unlocks:** Phase 5
**Produces:** `TmuxStatusDriver(config: NotifyConfig.Tmux)` with `start()` (immediate run + interval
timer), `stop()` (cancel timer, terminate in-flight, release lock), `refreshNow()` (immediate run
if idle).

**Done when:**
- [ ] DW-4.1: While a run holds the lock, a second attempt is skipped and logs `tmux.driver.skip`
      (single-instance proven).
- [ ] DW-4.2: `start()` performs an immediate run then repeats on the configured interval; `stop()`
      halts further runs and terminates any in-flight process.
- [ ] DW-4.3: `refreshNow()` triggers an immediate run when idle and is a no-op while one is running.
- [ ] DW-4.4: A missing/failed `claude` spawn is logged and does not crash or restart-storm.

**Difficulty:** HIGH
**Uncertainty:** grid-notify's ability to spawn `claude` (PATH/permissions) — verify before this phase.

### Phase 5: AppDelegate wiring + lifecycle + observers
**Model:** sonnet
**Skills:** welc-legacy-code, cc-defensive-programming
**Gate:** Full

**Goal:** Wire the dashboard window, viewmodel, watcher, and driver together in AppDelegate, with
`DistributedNotification` observers and window-bound driver lifecycle.

**Scope:**
- IN: a sprouted `setupTmuxDashboard()` in `AppDelegate.swift`; observers for
  `com.thegrid.tmux.toggle` and `com.thegrid.tmux.refresh`; window show ⇒ `driver.start()` +
  `watcher.start()`, hide ⇒ `driver.stop()` (+ stop watcher); `viewModel.onRefreshRequested =
  { driver.refreshNow() }`; teardown in `applicationWillTerminate`.
- OUT: the CLI/server that posts the notifications (P6).

**Constraints:** AppDelegate is untested GUI wiring — **sprout** a dedicated method instead of
bloating `applicationDidFinishLaunching`; keep new logic isolated and individually reasoned.
Lifecycle must be idempotent: starting an already-running driver is a no-op; hiding stops it
(cost guard). `[weak self]` in observers (mirror the existing `com.thegrid.notify.toggle` observer).
**Edge cases:** toggle when already visible/hidden; `refresh` while the window is hidden (run still
fires; visibility unchanged); duplicate observer registration on relaunch; terminate while a run
is in flight (driver.stop() releases the lock).

**Approach notes:** `toggle` controls window visibility **and** driver start/stop together (this is
the "window up ⇒ process running" contract); `refresh` only triggers a run.
**File hints:** `AppDelegate.swift` (existing watcher/ScriptManager/observer wiring at ~L60–140).
**Depends on:** Phase 2, Phase 3, Phase 4 | **Unlocks:** Phase 6
**Produces:** a wired grid-notify that, on `com.thegrid.tmux.toggle`, shows/hides the dashboard and
starts/stops the driver, and on `com.thegrid.tmux.refresh` (and the in-view button) calls
`driver.refreshNow()`; the watcher feeds `viewModel.load(_:)` live.

**Done when:**
- [ ] DW-5.1: `com.thegrid.tmux.toggle` shows the dashboard and starts the driver+watcher; a second
      toggle hides it and stops the driver.
- [ ] DW-5.2: With the dashboard open, a state-file change updates the tree live (watcher→viewModel).
- [ ] DW-5.3: `com.thegrid.tmux.refresh` and the in-view button both invoke `driver.refreshNow()`.
- [ ] DW-5.4: Hiding the window stops the driver (no further `claude` spawns); terminate releases the lock.

**Uncertainty:** None.

## Notes
- **Cost:** each tick launches a Claude Code run; cost scales with interval. Off-by-default; the
  driver only runs while the dashboard window is open.
- **Top risk:** headless skill-trigger reliability — mitigated by the command-file fallback and
  verified at DW-1.2 before the driver (P4) depends on it.
- macOS has **no `flock(1)`**; the mutex is `flock(2)` in Swift.
- `claude` is a python wrapper; resolve its absolute path before spawning (mirror `resolveThegridBin`).
- Atomic write (temp + rename) in the skill is required so the watcher never reads a partial file.
- grid-notify uses SwiftUI + `DispatchSource` (not actors); the actors-only/no-SwiftUI rule in
  `code-standards.md` §8 is grid-server-scoped.
